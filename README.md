## 1. API model та domain model

Розділено модель відповіді API та модель завдання, яку використовує інтерфейс.

Модель `ApiTodo` містить поля `id`, `todo`, `completed` і `userId`. Модель `Task` містить `id`, `title`, `description`, `completed`, `priority` та `category`.

У repository реалізовано функцію `toTask`, яка перетворює дані API на модель застосунку:

- `todo` перетворюється на `title`;
- `id` та `completed` зберігаються;
- для опису встановлюється порожній рядок;
- для категорії встановлюється `General`;
- для пріоритету встановлюється `medium`.

Поля опису, категорії та пріоритету обробляються як клієнтські metadata поточної сесії та не надсилаються як непідтримувані поля API.

## 2. HTTP client

Створено окремий модуль `src/api/httpClient.ts`.

HTTP-клієнт:

- будує URL на основі змінної середовища;
- виконує запити через `fetch`;
- встановлює заголовки для роботи з JSON;
- перевіряє `response.ok`;
- перетворює відповідь із JSON;
- передає помилки на вищий рівень;
- підтримує передавання `AbortSignal`.

Додано модуль `errors.ts` із класом `ApiError`, розпізнаванням скасованих запитів і формуванням повідомлень для користувача.

Прямі HTTP-виклики в UI-компонентах відсутні.

## 3. Repository Pattern

Створено `src/repositories/taskRepository.ts`, який приховує endpoint-и, формат DTO та перетворення даних.

Реалізовано такі методи:

| Метод | Призначення |
|---|---|
| `getAll()` | Отримання сторінки завдань |
| `getById(id)` | Отримання деталей завдання |
| `create(draft)` | Створення завдання |
| `update(id, changes)` | Оновлення завдання |
| `delete(id)` | Видалення завдання |

## 4. Завантаження списку та пагінація

Реалізовано завантаження завдань під час відкриття застосунку через `taskRepository.getAll()`.

Для пагінації використовуються параметри `limit` і `skip`. Розмір серверної сторінки становить 10 записів. Зміщення обчислюється за формулою:

```ts
skip = (page - 1) * PAGE_SIZE
```

Додано кнопки «Попередня» та «Наступна», індикатор поточної сторінки та кнопку «Оновити список».

Кількість сторінок обчислюється на основі серверного `total`. При зміні сторінки попередній незавершений GET-запит скасовується.

## 5. Loading, error, empty та success

Реалізовано окремі стани інтерфейсу:

| Стан | Реалізація |
|---|---|
| Loading | Повідомлення про завантаження списку або деталей |
| Error | Повідомлення про помилку та кнопка повторної спроби |
| Empty | Повідомлення про відсутність завдань або результатів фільтрації |
| Success | Відображення отриманих даних і повідомлення після успішних змін |

Для повідомлень використано компонент `Toast`. Виклики `alert` не застосовуються.

## 6. Деталі завдання

Створено компонент `TaskDetails`.

При виборі серверного завдання виконується окремий GET-запит через `taskRepository.getById(id)`. У деталях відображаються назва, опис, категорія, пріоритет і стан виконання.

Стан завантаження деталей зберігається локально в компоненті. Передбачено обробку помилок, повторну спробу та скасування запиту при закритті або зміні вибраного завдання.

Для записів, створених у поточній сесії, repository повертає локальні дані, оскільки DummyJSON не зберігає такі записи на сервері.

## 7. Створення завдання

Форму створення підключено до `taskRepository.create()`.

Перед надсиланням перевіряється назва завдання: порожнє значення або рядок лише з пробілів не допускається.

Створення виконується запитом `POST /todos/add`. Після успішної відповіді:

- нове завдання додається до інтерфейсу;
- форма очищується;
- показується повідомлення про успіх;
- за потреби відкривається перша сторінка списку.

При помилці введені дані залишаються у формі.

Для нових записів використовуються унікальні від’ємні id поточної сесії, щоб уникнути колізій через повторні id у симульованих відповідях DummyJSON.

## 8. Оновлення та видалення

Для серверних завдань реалізовано:

- редагування назви через PATCH;
- перемикання `completed` через PATCH;
- видалення через DELETE.

Перед видаленням показується inline-підтвердження з кнопками «Так, видалити» та «Скасувати». Запит надсилається лише після підтвердження.

Список оновлюється після успішної відповіді API. При помилці попередні дані зберігаються. На час виконання операції повторні зміни блокуються.

Подальше редагування та видалення новостворених записів repository виконує в пам’яті поточної сесії через обмеження DummyJSON.

## 9. Скасування запитів

Для GET списку та деталей використано `AbortController`.

Його `signal` передається через repository до HTTP-клієнта. Cleanup функції `useEffect` викликає `controller.abort()`.

Додатково перед оновленням React-state перевіряється `signal.aborted`. Це запобігає застосуванню застарілих відповідей після зміни сторінки або вибраного завдання.

Скасовані запити не відображаються як звичайні помилки завантаження.

## 10. Архітектура стану

Розділено серверний та клієнтський стан.

**Server state:** завдання поточної сторінки та загальна кількість серверних записів.

**Client/UI state:** фільтр, номер сторінки, вибраний id, редагований id, чернетка форми, підтвердження видалення та повідомлення.

У `localStorage` зберігається лише фільтр. Серверні завдання не використовують локальне сховище як друге джерело даних.

Оскільки DummyJSON не зберігає mutation постійно, repository підтримує журнал успішних змін у пам’яті. Він дозволяє зберігати результати створення, редагування та видалення при переходах між сторінками. Після перезавантаження вкладки журнал очищується.
